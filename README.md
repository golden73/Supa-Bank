## Rules
Parameterized queries only (`?`). Money is integer cents. Use `@login_required` / `@admin_required`.
Filter by `g.user["id"]`, never a user-supplied ID. Never log secrets. Feature branches + PR review.

## Implemented — Functionality 2 (Audit, branch `func/audit`)
- `app/routes/audit.py`: admin-only `/admin/audit` view. Renders `admin_audit.html`
  with the latest 200 `audit_log` rows (newest first). Viewing the audit log itself is
  recorded via `audit("view_audit")`.
- Anomaly alerts (computed on demand over the last 60 min, thresholds overridable via
  app config without touching the shared `config.py`):
  - **Brute force** — `login_failed` count per IP ≥ `AUDIT_FAILED_LOGIN_THRESHOLD` (5).
  - **Large transfer** — any `transactions.amount_cents` ≥ `AUDIT_LARGE_TRANSFER_CENTS` (10000).
- `app/templates/admin_audit.html`: accessible table + alert list extending `base.html`.
- `tests/test_audit.py`: anonymous redirected, customer gets 403, admin sees the page,
  no password hash/secrets leak, both alert paths fire.
- What is logged: non-sensitive actions + targets only (action name, transfer reference,
  IP, user_id, timestamp). Passwords/hashes/tokens are never passed to `audit()`.

## Known limitations (Functionality 2)
- Alerts are computed per-view (stateless), not persisted as tickets.
- "Large transfer" detection reads `transactions` directly; once the Lead's transfer route
  is live, the `audit("transfer", reference)` rows will align with these alerts.
- Time window uses SQLite `datetime('now', …)` (UTC); the page labels timestamps UTC.

## Threat Model (Functionality 2)

The audit functionality is designed to record administrative and security-relevant actions without leaking sensitive data. The following threats are considered:

- **Information disclosure**: The audit log should not contain sensitive data such as passwords, session tokens, or personal data. The `audit()` helper only accepts an action name and a non-sensitive target (e.g., transfer reference). This ensures that even if the audit log is exposed, no sensitive data is leaked.

- **Tampering**: The audit log is append-only in the sense that rows are only inserted, never updated or deleted by the application. However, the database user used by the application could potentially execute arbitrary SQL. To mitigate, the application uses a least-privilege database user (to be configured by the Lead) and only grants INSERT and SELECT on the audit_log table.

- **Unauthorized access**: The audit view is protected by the `@admin_required` decorator, ensuring that only administrators can view the audit log. The anomaly alerts are also only shown to administrators.

- **Log spoofing**: Since the audit log entries are generated by the application, there is a risk that an attacker could influence the action or target fields. The application validates that the action is from a fixed set (e.g., 'login_failed', 'transfer', 'view_audit') and the target is either a reference string (for transfers) or a generic string (like 'auth' for login failures). No user input is directly used as the action or target without validation.

- **Denial of service**: The audit view limits the number of rows to 200 by default, configurable via app config. The anomaly alerts are computed over a limited time window (default 60 minutes) and with thresholds to avoid excessive computation.
